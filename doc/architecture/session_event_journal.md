# Session Event Journal

`EventEnvelope` in `src/ai_game_player/event_journal.py` is the versioned session-event contract. Each record carries an event/session ID, a contiguous one-based session sequence, a UTC timestamp, a process-monotonic timestamp, event type/status, optional frame/turn/snapshot/correlation IDs, a compact JSON payload, and typed artifact references. `config/session_event.schema.json` describes schema version 1. Large media or model output belongs in the content-addressed Artifact Store; only its `ArtifactReference` is recorded here.

## Storage and recovery

The v1 backend is one SQLite database in WAL mode per session, with one active `EventJournal` writer instance per database. The writer lock serializes concurrent calls through that instance; separate writer instances must not target the same path. Each append inserts one compact envelope and commits its own transaction with `synchronous=FULL`. `flush()` and `close()` additionally request a full WAL checkpoint. Large media and model output are not stored in the database; use `ArtifactReference` to point to the content-addressed Artifact Store.

SQLite provides atomic transaction recovery: an interrupted, uncommitted append is rolled back by SQLite, while committed events remain available. Each append transaction writes the event and updates the metadata's committed-sequence high-water mark together. Opening an existing database validates that the high-water mark equals the final stored sequence, so deleting a committed tail event fails closed instead of allowing its sequence number to be reused. Opening also validates the database and envelope schema versions, session identity, event IDs, and contiguous sequence numbers. A malformed committed record fails closed and is never silently skipped. Reopening without an explicit session ID resumes the session in database metadata. Start a new session at a new database path (or reject a mismatching session ID) rather than mixing sessions in one database.

The journal preserves JSON decimal tokens exactly. Recovery parses fractional and exponent-form numbers as Python `Decimal`, so payload values such as `1e400`, `0.1000000000000000000000000001`, and `1e-10000` do not overflow, round, or underflow through binary floating-point conversion. `EventEnvelope.to_dict()` keeps those payload values as `Decimal`, and the journal JSON encoder writes them as JSON number tokens. A consumer that parses the stored JSON independently must pass `parse_float=Decimal` to Python's `json.loads()` to retain the same precision.

## Legacy Trace, History, Safety, and Runtime Log migration

When the application creates a `DecisionPipeline` for a new runtime session, `RuntimeComposition` creates a new database at `data/games/<game>/session_events/<session-id>.sqlite3`. `DecisionPipeline` gives that session's `EventJournal` to the decision, execution, Safety audit, and RuntimeLog adapters. The journal path and Session ID are unique for each runtime session.

Before the first migration of game history, each adapter reads its legacy source without deleting or rewriting it. `history.json`, `decision_trace.json`, `execution_history.json`, and `action_safety.json` are JSON arrays. The adapter validates each source record, stores the original record under `payload.legacy_record`, and assigns a stable migration event ID from the record type, file name, source position, and record content. `RuntimeComposition` serializes migration for the same game directory with an operating-system file lock. It creates `session_events/legacy_migration_v1.complete` only after the game-history migration succeeds, so later Sessions do not append the same legacy records to another Session Journal. Before the first import, RuntimeComposition atomically records the new Journal filename and planned completion markers in `legacy_migration_v1.pending`. Completion markers are published only after the pipeline factory has migrated every planned source. If the process stops before any planned marker is published, the next startup deletes that incomplete Journal and retries from the unchanged legacy sources. If at least one planned marker exists, the factory had completed; startup keeps the Journal, publishes any remaining planned markers, and removes only the stale pending record. Cleanup leaves the pending record in place until every marker and database removal succeeds, so a later startup can retry incomplete cleanup. Later history adapters still read retained sources when their legacy readers need a compatibility cache, but they do not replay those records into the new Journal.

RuntimeLog migration has its own completion marker beside the canonical RuntimeLog JSONL source because `RuntimeComposition.create_session_runtime()` accepts `runtime_log=None` and different game directories may share one application-wide log. The application creates the RuntimeLog marker only when a compatible logger is supplied and its old JSONL has been considered for migration. A later Session can therefore migrate the old application log even if an earlier Session ran without a RuntimeLog. A changed JSONL source path has its own marker and lock. When the RuntimeLog adapter neither retains records nor migrates them, the adapter skips reading the JSONL entirely.

`RuntimeComposition` inspects an injected pipeline factory before creating a Session Journal. A factory must accept `event_journal`, `migrate_legacy`, and `migrate_runtime_log`, either as named parameters or through `**kwargs`, to use Session Journal migration. An older factory that lacks those parameters still receives the legacy pipeline arguments it declares, and `RuntimeComposition` does not create migration markers for that factory. RuntimeLog migration uses a completion marker and interprocess lock beside the canonical RuntimeLog source path, so one application-wide log is imported once even when different game directories use it. A changed RuntimeLog path has a different marker and can be imported independently. Windows waits up to 30 seconds to acquire a migration lock, then raises a timeout error instead of waiting indefinitely. If pipeline initialization fails after a new Session Journal has received partial migration records, `RuntimeComposition` closes and removes that Session's SQLite file and sidecars, then leaves newly created migration markers absent so a later startup can retry. Provider creation remains owned by RuntimeComposition until the migration lock and all pipeline initialization steps succeed; every setup failure closes the Provider. An older injected pipeline that does not expose `load_execution_history()` remains usable; its metrics call returns an empty list instead of failing after a successful decision or execution.

After migration, decision history, decision trace, execution history, and Safety audit writes go to SQLite rather than rewriting their complete legacy JSON arrays. Their in-session readers retain the original record shape and the legacy JSON reader's float behavior; the Journal payload preserves fractional numeric tokens as exact Decimal values. RuntimeLog continues appending one JSONL line for existing tools and also appends the same event to the active Session Journal. RuntimeLog serializes attach, detach, and append operations with one lock, so shutdown cannot close the Journal during a log append. Each active Session owns its RuntimeLog attachment through a token; RuntimeLog rejects overlapping Session attachments and only the token owner can detach. The Session controller records each terminal state before closing the runtime. If executor or Provider cleanup fails, the pipeline writes a `session.shutdown_failed` RuntimeLog event with `status=failed` before closing the Journal. Pipeline shutdown checkpoints the Journal while RuntimeLog is still attached and records checkpoint failures before detaching; the Journal's close method still closes its connection after a checkpoint error.

The legacy files remain available as migration sources and are not deleted. Session journals created after migration remain separate databases. Aggregating records across multiple Session databases is not part of this adapter change; a future query layer must provide that behavior without scanning a complete journal on every gameplay step.

`tools/benchmark_event_journal.py` compares the production SQLite journal with a JSONL reference so implementers can measure append durability, recovery time, and storage size for the same 1,800-event workload. The default event count represents a 30-minute session at one event per second, and the default payload contains 128 bytes. JSONL flushes and calls `fsync` after every record by default; SQLite commits every append with `synchronous=FULL`. The throughput timer includes opening and initializing each backend. Per-event p50/p95 latency ends when the record reaches its durability point, including time waiting for a JSONL batch flush when `--jsonl-fsync-every` is greater than one.

To repeat the published workload on Windows, run `python tools/benchmark_event_journal.py --events 1800 --payload-bytes 128` three times on the same machine and compare the medians. The script creates temporary files and removes them when each run finishes. On 2026-10-09, three CPython 3.14 runs recovered all 1,800 records and checked session ID, contiguous sequence, unique event ID, and monotonic order within each epoch in both backends. Median throughput including backend initialization was 1,005 events/s for SQLite WAL and 1,186 events/s for JSONL. Median p95 durable-append latency was 1.286 ms for SQLite and 1.056 ms for JSONL. Median reopen validation took 70.67 ms for SQLite and 54.81 ms for JSONL. Median storage was 1,323,008 bytes for SQLite and 1,002,186 bytes for JSONL. These Windows measurements are local sizing evidence, not a cross-machine performance guarantee; SQLite is selected for atomic transaction rollback rather than peak throughput.

The journal now records decision history/trace, execution results, Safety audit outcomes, and active-session RuntimeLog events. `GameSessionController` still does not expose a journal query API, and Timeline/Video/Learning consumers cannot search across Session databases yet. Issue #263 owns indexed query and timebase APIs; this document does not claim those consumers are integrated.
