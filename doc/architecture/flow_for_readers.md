# 一回の判断と実行は、何をどの順番で行う？

[見取り図の索引へ戻る](README.md) ｜ [部品と実行場所を見る](runtime_map_for_readers.md)

**この図で確かめたいこと：** 新しい画面から候補を作り、前回操作の結果を含めて今回の判断をし、安全確認を通ってから必要に応じて入力する順番です。実入力がない判断だけの経路も区別します。

## 図1：通常の一回の流れ（現在の接続）

```mermaid
sequenceDiagram
    participant U as 利用者と画面
    participant P as 一回の処理
    participant O as 画面取得・認識
    participant E as 候補評価・結果評価・判断
    participant S as 回答・安全・停止の検査
    participant X as 入力実行
    participant G as 対象ゲーム

    U->>P: 今回の判断を始める
    P->>S: 開始時の停止・実行世代を確かめる
    alt Windows連続実行
        P->>O: 新しい画面を取得し、観測と候補を登録する
    else 単独の判断・実行
        Note over P,O: GUIに登録された観測を使う。画面取得は別操作
    end
    P->>O: 登録された観測と候補を読み出す
    O-->>P: 画面・時刻情報・候補の集合
    opt 実入力経路で同世代の未観測receiptがある
        P->>E: 実操作後観測を明示完了する
        Note over E: 元操作の結果を世代guard内で一度だけ保存
    end
    P->>E: 画面と候補を渡す
    Note over E: 候補評価と、公開済み実操作結果から判断材料を作る
    E->>E: 判断材料を組み立て、候補を選ぶ
    E->>S: 判断の回答を検証してもらう
    S-->>E: 検証結果
    E-->>P: 検証された判断と選択候補
    alt 判断だけを行う
        P-->>U: 選んだ候補・理由を表示
    else 入力を試みる
        P->>S: 同じ画面・候補・停止世代で安全を確認する
        alt BLOCK・停止、または実入力時の追加確認不足
            S-->>P: 入力しない理由
            P-->>U: 拒否・停止を記録して表示する
        else 条件を満たす
            S-->>P: 入力の検査を通過
            P->>X: 実行の依頼
            alt 確認運転
                X-->>P: 実入力せず結果を記録
            else 実入力の明示許可がある
                X->>G: キー・マウス入力を送る
                X-->>P: 送信証拠を元判断・世代のreceiptへ記録
            end
            P-->>U: 判断・実行の結果を表示する
        end
    end
    Note over O,G: 次の新しい画面で実際の変化を確認する
```

**線の読み方：** `->>` は処理を依頼する向き、`-->>` は情報・結果が戻る向きです。戻ってきた結果だけで「目的達成」を断定しません。必要な記録は履歴にも結び付きますが、説明を簡潔にするため、この図では保存先を独立した参加者として描いていません。

## 図2：続行できないときは？

```mermaid
flowchart TD
    A["登録した観測を読む。連続実行は新画面を取得"] --> B{"観測・候補の取得に成功？"}
    B -->|いいえ| Z["理由を表示・記録し、入力しない"]
    B -->|はい| C["候補の評価"]
    C --> R["明示観測で公開済みの同世代実操作結果から判断材料を作る"]
    R --> D{"許可できる候補はある？"}
    D -->|いいえ| Z
    D -->|はい| E["今回の候補を選ぶ"]
    E --> F{"回答は検査を通った？"}
    F -->|いいえ| Z
    F -->|はい| G{"停止・世代・安全条件は有効？"}
    G -->|いいえ| Z
    G -->|はい| H{"実入力の許可がある？"}
    H -->|いいえ| I["確認運転として記録"]
    H -->|はい| V{"追加確認・信頼性の条件を満たす？"}
    V -->|いいえ| Z
    V -->|はい| J["対象・期限・SafetyGuard等を確認して入力を試みる"]
    I --> L["計画記録のみ。実操作結果を作らない"]
    J --> K["実行receiptへ次の明示観測を関連付ける"]
```

- **最初の一回：** 同世代の実操作receiptがなければ結果イベントを作らず、判断材料には「不明（前回操作なし）」を渡します。
- **候補がない：** 利用可能な候補を捏造せず、選択や入力を中止する場合があります。
- **画面が古い・読み取れない：** 観測側の条件に従って失敗を伝えます。古い画面を新しい画面に見せかけません。
- **停止中・世代が古い：** 停止で無効になった世代の回答は検査で拒否します。ただし、入力器の最終停止確認とOSへの送信は不可分ではなく、確認直後に停止した場合や送信中の入力を完全に取り消す保証はありません。
- **安全上の拒否：** 「モデルの回答がもっともらしい」だけでは入力を許しません。
- **時間切れ：** モデルや画面取得等の処理が時間切れになることと、ゲーム内で失敗することは別です。処理を再試行する保証はここでは宣言しません。
- **確認運転（dry-run）：** OS入力なしの実行結果を記録します。実入力時だけの追加確認不足では拒否しませんが、BLOCKや停止等は別に検査します。

## 「前回の結果」は、いつ調べる？

例えば、前回「開始」を押したという記録がある場合、次に取得した画面でメニューが消えたか、別画面へ進んだかなどを調べます。その結果を今回の判断に渡します。**キー入力APIの送信成功はゲーム画面の変化の証拠ではありません。**

**実行事実との対応：** `GamePlayerEngine.step()`は判断計画だけを保存します。正常送信のreceiptをsnapshot・action・実行世代へ固定し、次の明示観測を元操作へ一度だけ関連付けます。判断のみ・確認運転・入力前失敗は実操作pendingを更新しません。Windows入力器は前処理後の入力API呼出し直前でdispatch信号を立て、送信後例外や送信不明はunknownに留めます。最後の操作もSession終了前の明示観測の対象にし、観測失敗を成功へ置き換えません。入力API到達とゲームへの効果は別です。詳細と検証範囲は [実行受領記録](execution_receipts.md)、停止・入力境界の残る制約は [#612](https://github.com/tomiya7688/AI_game_player/issues/612) を参照してください。

通常Sessionは#421のModeと#422の有限workerを所有し、各判断の開始時に安全境界を確認して知識の一版を固定します。検証済み効果と安定識別がある場合だけ数値知識を更新し、入力権限や安全規則は変更しません。識別の既定は無効、一般的な因果検証providerは未接続です。[接続条件と限界](light_adaptation.md)を参照してください。

具体的な結果の統合方法は [OutcomeDetectionFusion機能説明書](../OutcomeDetectionFusion機能説明書.md)、判断材料の作り方は [DecisionContext機能説明書](../DecisionContext機能説明書.md) にあります。

## 根拠と未確認の範囲

確認した主な場所（2026-11-01、Issue #628の実行受領記録を反映）：

- [`pipeline.py`](../../src/ai_game_player/pipeline.py)：観測と候補の取得、判断・安全・実行の接続、停止状態の確認。
- [`engine.py`](../../src/ai_game_player/engine.py)：候補評価、前回結果、判断材料、回答検証、履歴。
- [`observation_service.py`](../../src/ai_game_player/observation_service.py)：観測と候補のための画面取得。
- [`decision_verifier.py`](../../src/ai_game_player/decision_verifier.py)：判断と画面・許可候補の照合。
- [`run_control.py`](../../src/ai_game_player/run_control.py)：停止や再開に関わる制御。
- [`action_safety.py`](../../src/ai_game_player/action_safety.py)、[`action_executor.py`](../../src/ai_game_player/action_executor.py)：入力前の評価と実行。

**確認したのは静的な処理順です。** Windows実機での操作成功、全失敗経路の試験実施、実在モデルの稼働、GUI幅ごとの表示検査はこのページで完了していません。局所的な正しさやテストの合否を図の存在だけで保証しません。残作業は [#608](https://github.com/tomiya7688/AI_game_player/issues/608)、安全は [#612](https://github.com/tomiya7688/AI_game_player/issues/612) で追います。
