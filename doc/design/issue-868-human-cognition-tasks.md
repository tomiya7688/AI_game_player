# Issue #868 人間のゲームプレイ中の認知をタスクとして洗い出し、タスク別のモデル・手法を割り当てる

## 成果物
設計資料のみ。コードは変更しない。実装は「子Issue案」の単位で別Issueにする。

## 利用者の操作
利用者の操作はありません。設計方針の合意だけが必要です。

## 背景
[#866](issue-866-decision-architecture.md)のD9で、判断を「タスク」、実行を「worker」に分けた。人間がゲームをプレイする時に暗黙に行っている脳の判断は、全てタスクと言える。そこで、認知科学・ゲームAIの文献と実システムを調べ、必要なタスクを洗い出し、各タスクにどんなモデル・手法を与えるかを設計する。ゲームごとに必要な評価関数の生成と改善も、このタスクに含める。

## 対象範囲
対象: 認知タスクの洗い出し、既存の判断機との対応、タスク別の候補手法と根拠、評価関数の生成・改善・自己欺瞞の防止、子Issue案。対象外: コード、数値、モデルの最終選定、学習・知識増築ループの本体（[#800](https://github.com/tomiya7688/AI_game_player/issues/800)）。

## 評価関数の生成・改善・自己欺瞞の防止
ゲームごとの評価関数（進捗・成功・失敗の指標）の生成と改善も、タスクとして扱う（X3の中核）。ただし、評価の正本は[自律Playerと権限分離](../architecture/autonomous_player_goal_authority.md)の「評価の四層」であり、本資料はそれを置き換えず、各段階に**どんなworker・手法を与えるか**だけを決める。

| 四層の段階 | 既存の担当 | 本資料のタスク |
|---|---|---|
| ゲーム内で何が価値かの仮説（`value_hypotheses`、代替案は最低2種類） | goal authority | E1の入力。代替案の候補を安く出す |
| どう測るかの設計（`EvaluationDesignPlan`、#844） | #844 | E1 |
| 評価器の生成（#771/#772） | #771/#772 | E1（生成）、E2（改善） |
| 評価器の信頼性（#773）、独立比較（#173/#171/#780） | #773、#173、#171、#780 | E2（選択）、E3（検証） |

評価器の出力は**Typed DSL/Registryの仕様**に限る。任意のコードを実行する形にはしない（Eureka系の「報酬関数のコード」をそのまま実行することは避ける。安全性の問題と、DSLの方針に反するため）。

### 設計するパイプライン
1. **E1 生成（安い信号から先に）。** 画面から検出できるものを先に固定する（スコア領域のOCR、ゲームオーバー画面の判定、画面変化量）。ここは規則・小型分類器で作る。次に、LLM/VLMに、画面サンプルとゲーム説明から、価値の仮説と進捗の候補指標を**複数**（最低2種類）提案させる。出力はTyped DSLの仕様で、画面から計算できて単調に進みやすい指標。観測可能なサブゴールの有限状態（報酬機械風）で整理すると診断しやすい。
2. **E2 改善（外部の基準で選ぶ）。** 候補を進化的に変異・選択する（FunSearch/AlphaEvolveの形）。選択の基準は、自分の指標ではなく、**外側のもの**に置く（下記の外部基準）。指標を最適化する側と評価する側のモデルは分ける。内発的動機は、評価関数が停滞した時の探索用に別枠で使い、評価関数にはしない。
3. **E3 自己欺瞞の防止（最重要）。**
   - **保留データ。** 改善に使わなかった対局を取っておく。保留データには、**複数の方策**（現在の方策、過去の方策、ランダム）の軌跡を入れる。古い方策だけでは、新しい方策のハッキングを検出できない。方策または挙動が変わった場合は、評価器を**再検証**する。新しい方策で生成した保留軌跡と、候補の順位付けに使う評価器とは独立した指標で再検証し、検証が済むまで、その評価器の高評価を順位付けに使わない。
   - **負の対照を必須にする。** 独立した証拠で「Goalの進捗が無い」と確認できた区間（無操作、ランダム操作、入力停止など）で、指標が上がらないこと。実際の進捗が独立して確認された区間で指標が上がっても、失敗とはみなさない（放置しても進むゲームがあるため）。時計・タイマー・画面の散らかり具合のように、時間と相関するだけの特徴で指標が上がっていないことは、引き続き要件とする。
   - **指標の版を、実験の前に固定する。** 実験の途中で指標を差し替えない。
   - **真の指標がない場合。** スコアやクリアが無いゲームでは、Playerが設定したGoal固有の成果（独立して検証できるもの）も外部基準として認める。保留データと負の対照などの検証を通過した評価器は昇格できる。外部基準を独立して検証できない場合に限り、評価の確信度に上限を置き、評価器を昇格させない（探索用の補助にとどめる）。
   - **独立性。** 同じフレーム・同じOCRから作った複数の指標は、独立ではない。独立と数えるには、観測の経路か導出方法が異なる必要がある。不一致は警戒信号にする。
   - **判定役の分離。** 自己批評には、実行結果と画面差分という証拠を必ず添える。同じモデルに自分の成果を採点させない。
   - **人間のラベル・確認の扱い。** 友達（GUI利用者）は評価重みを強制変更できない。人間のラベルは、provenance付きの証拠として、**保留データでの検証だけ**に使い、重みの設定には使わない。通常の実行では人間がいない前提なので、人間がいない時は、負の対照と複数方策の保留データによる検証だけで進める（人間の確認があれば、確信度の上限を緩める根拠として記録する）。

外部基準の例: 独立した結果の証拠（スコア、クリア、Goal固有の成果）で、画面間の進み具合の順序を判定し、評価器の順序との一致率を見る。時系列の前後だけを進捗の根拠にはしない（時間と相関する特徴で満たされるため）。独立した証拠で判定できない画面の対は、選択の基準から除外する。別モデルや人間の選好ラベルとの一致率は、保留データでの検証にだけ使う。既知のよい/悪いプレイの区別能力も使える。

注意: Eureka系は環境のコードが見える前提で、画面のみの本件にはそのまま適用できない。VLM系のゲーム画面への一般化は未検証である。画面のサンプルをVLM/LLMへ送ることは、privacy区分の対象になる（下記）。

## privacy区分
画面のサンプル（フレーム）をVLM/LLMへ渡す経路は、既存のdata class（`raw_frame`、`cropped_image`。`privacy_data_inventory`、Provider契約の送信data class）で足りるかを**先に確認**する。現行は、生のフレームを遠隔へ送る経路が無く、Remote Providerは既定でOFFである。VLM固有の制限（ローカルのVLMだけに限る、VRAMはAdmissionで承認する）が既存のclassで表せない場合に限り、新しい区分を追加する。#866 D8の`macro_decision`は別途追加する。子Issue mで扱う。

## 実システムからの設計上の示唆
- **呼出しの契機は、タスクの開始、サブゴールの完了または失敗、検証の失敗やエラー、人間の発話の4種が主**で、毎フレームの定周期で重い層を呼ぶ例は少ない（Voyager、SayCan、Inner Monologue、PUBG Ally）。#864のMacroTriggerに、`subgoal_done`と`verification_failed`を追加する候補がある。
- **役割分担は3パターン**: (a) 重い計画器がサブゴールやコードを出し、軽い制御器が実行する（SayCan、Plan4MC、JARVIS-1、PUBG Ally）、(b) 単一モデルが毎フレーム低レベル行動まで出す（VPT、SIMA）、(c) 重いVLMを毎ステップ呼ぶ（CRADLE、UI-TARS、Claude computer use）。(c)は遅く、高速戦闘に弱い。本システムは(a)を採る。
- **知覚は分離する**（OmniParser型: OCR＋検出＋キャプション）。VLMには必要な時だけ画像を渡す。
- **学んだ手順は、実行可能なコード＋説明の埋め込みで保存**する（Voyager型）。事前にスキルグラフを作るPlan4MC型は、実行時のLLM呼出しを避けられるが、下位スキルはシミュレータでのRL（内発報酬つき）で学習しており、それは高価な学習の後の話である（Plan4MCのv2の題名は「Skill Reinforcement Learning and Planning for Open-World Long-Horizon Tasks」）。Voyagerの自己検証は、Mineflayer APIの状態を使っている。どちらも、**画面だけのゲームでは前提がそのままは成り立たない**。
- **軽い選択器が重いモデルの挙動を切り替える**例（Agent57のバンディット）は、M6のRouter/Cascadeの参考になる。
- **PUBG Allyは、行動木がティックごとの移動・照準・戦闘を担当し、2BパラメータのSLMが意図理解・連携・発話を担当する**。ローカルで動かし、クラウドLLMは遅すぎるため避けた。この分担は、本システムのX1（反射）とマクロ層の分担に近い。ただし、行動木もSLMも、決定的なPUBGの仕様、tool呼出し、テキスト化したゲームエンジンの状態を入力にしており、画素は読んでいない（**特権的な状態を使っている**）。画面だけのゲームには、そのまま当てはまらない。戦闘の能力の評価は高くなかったという報道もある（二次情報）。
- 人間らしさが必要なら、AlphaStarとOpenAI Fiveのように、行動頻度と反応遅延を明示的に設計する。
