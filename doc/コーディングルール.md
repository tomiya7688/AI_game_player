# 共通コーディングルール

この文書は、AI Game Playerのコード、テスト、文書を変更するすべての作業者（人、Claude Code、Codex、ChatGPT、GitHub Copilot）が守る規則です。変更前に読み、PR作成前の自己レビューで適合を確認します。

命名、責務分離、構造化コメント、性能、説明文の詳細は[コーディング規約](./コーディング規約.md)、具体的な差し戻し条件は[レビュー基準](./レビュー基準.md)に従ってください。この文書は共通の入口と、PR本文へ記録する自己レビュー7観点を保持します。

## クラスとファイル

- 原則として、1つのクラスを1つのファイルに定義します。複数クラスを同じファイルに置くのは、密接に関連する小さな補助クラスなど、同じファイルに置く理由が明確な場合に限ります。
- 1つのクラスは、ひとまとまりの責務を持ちます。複数の異なる理由で変更される処理は、別のクラスやモジュールに分けます。

## 関数とメソッド

- 1つの関数またはメソッドは、呼び出し側から見て一つの目的を果たします。複数の段階を実行する場合も、それらが同じ目的の処理を構成していることを確認します。
- 関数の名前と引数から、何を受け取り、何を行い、何を返すかを予測できるようにします。

## コマンド指向

- 完全に適用できない場合もありますが、処理の目的と依頼内容が明確になるよう、コマンド指向の設計を意識します。複数の役割が一つのクラスや関数に集まる場合は、コマンドや責務を分割できないか検討します。

## 本番コードの構造化コメント

- 対象は、新規・変更した本番コード（`src/ai_game_player/`、`native/include/`、`native/src/`）のクラス、関数、メソッド、およびC/C++構造体の宣言です。テスト、ツール、生成コードは対象外です。
- 宣言の直前にJSON風のコメントを置きます。Pythonでは`#`、C/C++では`//`を使います。書式とC/C++のヘッダー・実装間の配置は[コーディング規約のJSON-like Comment Outs節](./コーディング規約.md#json-like-comment-outs)に従ってください。
- クラスには「責務」と、保持する状態を説明する「フィールド」を書きます。状態を保持しないクラスも、「フィールド」に「なし」と理由を明記します。
- 関数・メソッドには「責務」「処理」「引数」「戻り値」を書き、送出する例外があれば「エラー」も書きます。引数名や型を言い換えるだけにせず、呼び出し側が知るべき意味、単位、条件を書きます。
- 行内コメントは、コードから読み取れない理由、制約、非自明な判断だけに使います。コードの逐語的な言い換えは書きません。
- コードを変更したら、そのコードに付いたコメントも同じ変更内で実装と照合して直します。

## 文章（文書・Issue・PR・エラー文）

- 読者がその文だけで対象、操作、条件、結果を特定できるように書きます。「これ」「それ」「上記」だけで対象を指しません。
- 「高速」「安全」「柔軟」などの評価語は、測定値、比較対象、具体的な条件のいずれかで裏付けるか、書きません。
- 現状、提案、未確認事項を区別します。根拠のない挙動や成功条件を書きません。
- 文体は、変更する文書の既存の言語と文体に合わせます。

## 変更の管理

- 新しい機能は、レビューとテストが可能な機能単位に分けてGitで管理します。1つのIssueを1つのブランチ・1つのPRで扱います。
- 変更のたびに対応するテストを追加・更新し、`doc/versions.md`の`Unreleased`へIssue番号と実装済みの振る舞いを追記します。
- PRの作成、CI確認、自己レビュー、マージの手順は[ワークフロー](ワークフロー/ワークフロー.md)に従います。
- 実装PRには、[レビュー基準の手法対照表](./レビュー基準.md#指定手法と実装の対応)を記録してください。指定手法、実装場所、本番経路への接続、検証証拠、未達成果物のOpen Issueを対応付けます。文書だけの変更など、適用されない項目には対象外の理由を記録してください。

## 自己レビューの観点

PRを作る前に、自分の差分を次の観点で確認します。記録方法はワークフローの「自己レビュー」に従います。

1. 正しさ: 入力境界、失敗経路、停止条件、状態遷移で誤動作しないか。
2. 安全: 実入力、削除、外部送信を既定で有効にしていないか。Safety / Verifierを迂回していないか。
3. 責務: 上記の「クラスとファイル」「関数とメソッド」に違反していないか。
4. 命名: 型、関数、変数が役割と一致しているか。
5. コメント: 構造化コメントが付き、実装と一致しているか。
6. テスト: 新しい振る舞いと失敗経路にテストがあるか。バグ修正は修正前に失敗する再現テストがあるか。
7. 文書: `doc/versions.md`と、実装で事実が変わった文書を更新したか。

## 継承の共通規約（必須・レビュー基準）

この節は、新規・変更するプロジェクト所有コードの設計者とレビュー担当者に適用します。具象クラスは、そのクラス自身のインスタンスを生成できるクラスです。抽象クラスは、そのクラス自身のインスタンスを生成できず、派生クラスの基底として使うクラスです。`A → B`は、BがAを直接継承する関係を表します。

### 禁止：具象クラス起点の連続継承

- **具象クラスAを継承するクラスBを、クラスCがさらに継承する構造を禁止します。** つまり、連続する3クラスの関係が`具象A → B → C`となる場合は違反です。中間のBが具象か抽象かは問いません。
- **`抽象A → 具象B → C`は、この禁止規則の違反ではありません。** ただし、設計と可読性のレビューを受けてください。さらにDを派生させて`具象B → C → D`となる場合は、禁止規則に該当します。
- この規則単独では、`具象A → B`という一段の継承を一律には禁止しません。ただし、プロジェクトに「具象クラスの継承自体を禁止する」などのより厳しい既存規則がある場合は、厳しい規則を優先してください。
- 言語に暗黙で存在する`Object`、`System.Object`、`java.lang.Object`などの最上位基底型と、インターフェースの継承・実装は、この違反判定の対象外です。

### 継承を選ぶ前の設計原則

- **具体的な処理を持つクラスの継承は原則として避けてください。** 抽象クラスでも、具体的な実装を持つ場合は同じ原則を適用します。継承関係そのものに意味がなく、処理の再利用だけが目的なら、別のオブジェクトに処理を任せる委譲や、複数のオブジェクトを組み合わせる合成を優先してください。
- 基底型と派生型に共通する意味のある契約が実際に存在する場合、または同じ契約を持つ型が今後必要になると合理的に予想できる場合に限り、継承を検討してください。「いつか使うかもしれない」という理由だけで抽象化や継承階層を作らないでください。
- 禁止規則に抵触しなくても、階層が読みにくい、責務を理解しにくい、変更が過大な範囲へ波及する、派生型を基底型の代わりに使うと契約が崩れるなどの問題があれば、レビューで不合格とします。禁止規則に抵触しないことは、設計の承認を意味しません。

### 適用範囲と例外

- 継承構造を意図的に採用する場合は、対象機能の設計判断を管理するGitHub Issue、またはそのIssueから参照する設計書へ、理由と適用範囲を明記してください。この記録がある箇所は例外とします。既存コードに同じ形があるという理由だけで、例外として扱わないでください。
- コンパイラや解析器が入力として扱う言語の継承仕様、サンプル、検証用fixture（テスト用の入力データ・コード例）と、プロジェクト自身の実装規約を区別してください。
- 新規・変更するプロジェクト所有コードへ適用します。無関係な既存コードを一斉に書き換える必要はありません。
