# 共通コーディングルール

この文書は、AI Game Playerのコード、テスト、文書を変更するすべての作業者（人、Claude Code、Codex、ChatGPT、GitHub Copilot）が守る規則です。変更前に読み、PR作成前の自己レビューで適合を確認します。

## クラスとファイル

- 原則として、1つのクラスを1つのファイルに定義します。複数クラスを同じファイルに置くのは、密接に関連する小さな補助クラスなど、同じファイルに置く理由が明確な場合に限ります。
- 1つのクラスは、ひとまとまりの責務を持ちます。複数の異なる理由で変更される処理は、別のクラスやモジュールに分けます。

## 関数とメソッド

- 1つの関数またはメソッドは、呼び出し側から見て一つの目的を果たします。複数の段階を実行する場合も、それらが同じ目的の処理を構成していることを確認します。
- 関数の名前と引数から、何を受け取り、何を行い、何を返すかを予測できるようにします。

## コマンド指向

- 完全に適用できない場合もありますが、処理の目的と依頼内容が明確になるよう、コマンド指向の設計を意識します。複数の役割が一つのクラスや関数に集まる場合は、コマンドや責務を分割できないか検討します。

## 本番コードの構造化コメント

- 対象は、新規・変更した本番コード（`src/`）のクラス、関数、メソッド宣言です。テスト、ツール、生成コードは対象外です。
- 宣言の直前に、`# {` と `# }` で囲んだJSON風のコメントを置きます。書式は `src/ai_game_player/engine.py` や `src/ai_game_player/baseline_provider.py` の既存コメントに合わせます。
- クラスには「責務」と、保持する状態（「フィールド」または「保持状態」）を書きます。
- 関数・メソッドには「責務」「処理」「引数」「戻り値」を書き、送出する例外があれば「エラー」も書きます。引数名や型を言い換えるだけにせず、呼び出し側が知るべき意味、単位、条件を書きます。
- 行内コメントは、コードから読み取れない理由、制約、非自明な判断だけに使います。コードの逐語的な言い換えは書きません。
- コードを変更したら、そのコードに付いたコメントも同じ変更内で実装と照合して直します。

## 文章（文書・Issue・PR・エラー文）

- 読者がその文だけで対象、操作、条件、結果を特定できるように書きます。「これ」「それ」「上記」だけで対象を指しません。
- 「高速」「安全」「柔軟」などの評価語は、測定値、比較対象、具体的な条件のいずれかで裏付けるか、書きません。
- 現状、提案、未確認事項を区別します。根拠のない挙動や成功条件を書きません。
- 文体は、変更する文書の既存の言語と文体に合わせます。

## 変更の管理

- 新しい機能は、レビューとテストが可能な機能単位に分けてGitで管理します。1つのIssueを1つのブランチ・1つのPRで扱います。
- 変更のたびに対応するテストを追加・更新し、`doc/versions.md`の`Unreleased`へIssue番号と実装済みの振る舞いを追記します。
- PRの作成、CI確認、自己レビュー、マージの手順は[ワークフロー](ワークフロー/ワークフロー.md)に従います。

## 自己レビューの観点

PRを作る前に、自分の差分を次の観点で確認します。記録方法はワークフローの「自己レビュー」に従います。

1. 正しさ: 入力境界、失敗経路、停止条件、状態遷移で誤動作しないか。
2. 安全: 実入力、削除、外部送信を既定で有効にしていないか。Safety / Verifierを迂回していないか。
3. 責務: 上記の「クラスとファイル」「関数とメソッド」に違反していないか。
4. 命名: 型、関数、変数が役割と一致しているか。
5. コメント: 構造化コメントが付き、実装と一致しているか。
6. テスト: 新しい振る舞いと失敗経路にテストがあるか。バグ修正は修正前に失敗する再現テストがあるか。
7. 文書: `doc/versions.md`と、実装で事実が変わった文書を更新したか。
