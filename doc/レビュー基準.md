# レビュー基準

## 背景

AI Game Playerは、画面認識・判断・入力・評価をつなぐアプリケーションです。コードや説明の小さな曖昧さが、誤操作、停止不能、評価誤り、保守負担につながることがあります。

## 目的

レビューで品質上の問題を見落とさず、修正理由と確認方法が分かる差し戻しを行います。本基準の禁止事項に該当する変更は承認・マージしません。

## 使い方

レビュアーは変更されたコード、テスト、仕様書、設計書、利用者向け説明に本基準を適用します。該当する項目を確認し、問題があれば対象ファイルと行、問題が起きる理由、必要な修正、再確認方法を示して差し戻してください。

判断に必要な実行環境がなく、CIやE2Eの結果を確認できない場合は「未確認」と記録します。未確認を成功扱いにしたり、実行したと報告したりしてはいけません。

## 差し戻し基準

以下のいずれかに該当する変更は差し戻します。好みだけで差し戻さず、該当する基準と具体的な根拠を示してください。

### コードの読みやすさと構造

- 文として読めず、処理の目的や条件を正しく読み取れません。
- 関数名、クラス名、変数名から、何をするか・どの値を表すか・必要な場合は型や単位を直感的に判断できません。
- 関連する状態と振る舞いを所有するまとまりがクラス化されず、変数や関数が複数箇所へ散らばっています。状態を所有しない単純な純粋関数まで、形式だけのクラスへ移す必要はありません。
- 1クラスが複数の独立した責務を持っています。
- 1関数が複数の処理単位を抱え、ひとつの目的として追えません。
- ファイルが長すぎて責務、処理のまとまり、変更箇所を追えません。一つの責務だけでも主要処理を把握するためにファイル内を何度も往復する必要がある場合は、具体的な分割境界を示して差し戻してください。単なる行数ではなく、分割できる責務や読解上の負担を根拠にします。
- 同じ処理や情報を重複して実装し、修正漏れや仕様不一致を招きます。
- 説明の価値がない一時変数・別名・中間関数などを増やし、処理を迂回させています。
- 意味を定義していないマジックナンバー、真偽値との不要な明示比較（例: `if enabled == True`）など、誤読や変更漏れを招く書き方があります。

### コメントと処理説明

- 本体コードのクラス、関数、メソッドに、[JSON-like Comment Outs](https://github.com/tomiya7688/Json-like-comment-outs)に準拠した宣言コメントがありません。
- C/C++の`struct`または`typedef struct`を新設・変更したのに、構造体の責務と公開フィールドの意味・単位・入出力の方向がコメントにありません。C ABIのフィールドも対象です。
- `native/include/`で公開する関数や型の説明が実装ファイル側にしかない、または同じ宣言コメントをヘッダーと実装ファイルの両方へ重複して書いています。
- 宣言コメントが対象の直前になく、責務、状態、処理概要、実際の入出力を読み取れません。
- 宣言名、フィールド名、引数、戻り値、例外の説明が、同じ例や実装の契約と一致していません。
- コメントが実装と食い違う、説明対象が曖昧、またはコードの逐語的な言い換えになっています。
- コメントに「処理する」「確認する」「値を返す」とだけあり、何を対象に、どの条件で、どんな結果になるか読み取れません。
- 引数の説明が引数名・型の繰り返しだけで、呼び出し元から何を渡す値か分かりません。戻り値も型だけで、各値の意味や呼び出し側の扱いが分かりません。
- 主要フィールドが保持する状態や利用時期が説明されず、名前の和訳しかありません。
- 読者に共有されていない略語・英単語・専門語が説明なしに続き、日本語として一度で意味を取れません。
- 記法や必須キーは揃っていても、コメントを読んだ人が宣言の目的・対象・重要な条件を自分の言葉で説明できません。
- 意味のある処理単位に、その目的・理由・境界を説明するコメントがありません。
- コメントが細かな行ごとの実況になり、実装と同じ情報を繰り返しています。

JSON-like Comment Outsの必須・推奨・任意の範囲と対象外は、[コーディング規約](./コーディング規約.md)に従います。宣言前コメントの必須項目が欠けた変更は差し戻します。通常コメントは処理単位を説明するために使い、各行を機械的に説明する必要はありません。

説明不足を指摘するレビューコメントには、対象箇所だけでなく、抜けている対象・条件・結果・用語のどれが読めないかを書きます。「コメントが悪い」「分かりにくい」だけの指摘は有効な差し戻し理由になりません。可能な場合は、意図を保った短い書き換え例か、書き足すべき契約を示してください。

### 正しさ、安全性、性能

- 入力、境界値、状態遷移、並行実行、失敗時の後始末などに、妥当なバグの可能性があります。
- 入力規模や実行頻度に対してアルゴリズムが非効率で、認識・判断・描画・入力などの応答性を損ないます。
- 不要な反復処理、重複I/O、不要なコピーや変換、ブロッキング処理など、実行性能に悪影響があります。
- ファイル、プロセス、ウィンドウ、ネットワーク、資格情報、実入力などへ危険な操作を行うのに、対象検証、権限境界、失敗時の停止・復旧、必要な利用者確認がありません。
- 既存のインターフェースや拡張点を不必要に壊し、新しい機能・Provider・処理系を安全に追加できません。
- その場しのぎの抽象化で複雑さを増やす一方、実際に必要な変更点や差し替え点を分離できていません。

### 検証

- リポジトリで必須とされるCI、静的検査、ビルド、テストが失敗します。
- CIの失敗を隠すためにチェックを削除・弱体化・回避しています。
- 変更の影響範囲に必要なE2Eテストが失敗します。
- バグ修正なのに再現テストがなく、理由または代替検証も説明されていません。
- E2Eを含む必須確認が未実施なのに、合格・完了として報告しています。

### 仕様書・設計書・説明文

- 人間が読んで仕様、判断根拠、変更点を理解できません。
- 背景、目的、採用する手段、利用者が行う操作や実行方法がなく、説明を単独で使えません。操作がない場合は「利用者の操作はありません」などと明記します。
- 日本語として不自然、曖昧、冗長、または用語が一貫していません。
- 利用者に操作を求める文で「してください」などの依頼表現を使っていません。
- アプリの動作を説明する文で「します」「なります」などのアプリを主語とする表現を使わず、利用者の操作と混同させています。
- 説明に必要な前提、制約、失敗時の挙動、確認できる結果が抜けています。

## 差し戻しコメントに含めること

各指摘では、次を短く具体的に示します。

1. 対象のファイルと行、または該当する資料の節
2. この基準のどの項目に違反するか
3. どの入力・状態・読み方で問題になるか
4. 必要な修正と、修正後に行うテスト・確認

複数の指摘を一つにまとめて曖昧にせず、重要な問題から並べます。問題がなく、必要なCIとテスト結果を確認できた場合にのみ、その範囲を承認可能とします。
