# コーディング規約

## 背景

AI Game Playerは複数の処理領域と言語を持ち、コードの生成・変更も継続します。名前、責務、コメント、エラー処理、説明資料の書き方が揃っていないと、変更の理解や安全性の確認に時間がかかります。

## 目的

本規約は、新規・変更するコードと関連資料を、読みやすく、安全に検証でき、後から拡張できる形に揃えます。違反は[レビュー基準](./レビュー基準.md)に従って差し戻します。

## 基本方針

- 1ファイルには原則として主となるクラスを1つだけ置きます。C++ではクラス宣言をヘッダーに置き、実装を対応するソースファイルへ分けます。
- 1クラスは1つのまとまった責務を持ちます。
- 1関数・メソッドは1つの処理単位を完了します。
- 状態とそれを操作する振る舞いがまとまって所有される必要がある場合は、クラスとして表現します。状態を所有しない純粋な処理を、形式だけのクラスへ入れる必要はありません。
- コマンド指向を意識し、処理を行う命令や変更点が呼び出し側から分かる設計にします。
- リポジトリの既存API、Issueの仕様、安全境界、対象言語の慣習を守ります。

## 名前と変数

- 関数名は、その関数の目的・動作・結果が名前だけで分かる動詞中心の名前にします。
- クラス名は、担当する責務やドメイン上の役割を表す名詞にします。
- 変数名は値の意味、必要な場合は型・単位・対象を表します。`count`、`value`、`data`などだけで意味が特定できない名前は避けます。
- 略語はチーム内で一般的なものに限り、局所的・独自の略記を作りません。
- 一時変数は、式を明確に分割する、意味を付与する、再利用するなどの役割がある場合だけ作ります。
- 同じ値の別名や、1回しか使わず意味も増やさない中間関数・変数は作りません。
- `if enabled == True`のような真偽値との明示比較は使わず、値を直接判定します。否定条件は読みやすい条件式にします。
- 意味の定義がない数値・文字列を埋め込みません。設定値や定数として名前を付け、単位と範囲を明らかにします。

## クラス、ファイル、関数

- クラスには一つの責務だけを持たせ、状態の不変条件と状態を変更する操作を同じ所有者にまとめます。
- 独立して変更・テスト・再利用するクラスは、ほかのクラスと同じファイルへ混在させません。C++では宣言と実装をヘッダー・対応ソースファイルの組で管理します。
- 関数には一つの目的を持たせます。検証、取得、変換、保存など、独立して説明できる処理単位は別関数へ分けます。
- 条件分岐やループを含む関数も、主要な流れを追える大きさに保ちます。詳細が増えたときは、明確な名前を持つ小さな処理へ抽出します。
- ファイルは一つの機能・責務の範囲に保ちます。複数の独立した責務を並べた長大なファイルは作らず、責務単位に分割します。一つの責務でも主要処理の把握に何度もスクロールやファイル内の往復が必要な場合は処理単位へ分割します。行数だけの機械的な上限は設けず、具体的な分割境界と読解負荷をレビューで判断します。
- クラス化は状態や不変条件の所有を明確にするために使います。名前のない処理を隠したり、単一関数を形式的に包んだりするために使いません。

## JSON-like Comment Outs

宣言コメントは、[JSON-like Comment Outs 日本語仕様](https://github.com/tomiya7688/Json-like-comment-outs/blob/main/docs/jp/SPECIFICATION.md) Draft v0.9 と[テンプレート](https://github.com/tomiya7688/Json-like-comment-outs/blob/main/docs/jp/TEMPLATE.md)に従います。日本語版を正本とし、チームが理解しやすい自然な日本語を使います。この形式はJSON風の構造化コメントであり、厳密なJSONではありません。

### 対象範囲

- 対象は本体コード `src/ai_game_player/` と `native/include/`、`native/src/` にあるクラス、関数、メソッドです。
- テスト、`tools/`、生成物はこの宣言コメントの適用対象外です。
- 新規宣言にはコメントを付け、変更宣言では実装とコメントを同時に更新します。
- コメントは対象宣言の直前に置きます。Pythonでは `#`、C++では `//` を使います。
- 関数・メソッド内部の処理単位、条件分岐、ローカル変数には通常コメントを使います。そこへJSON-like形式を適用しません。

### 必須項目

クラスには、責務と主要なフィールドを記述します。クラスが提供する重要な振る舞いが読み取りに必要な場合は、処理項目にも記述します。

関数・メソッドには、責務、意味のある順序で並べた主要処理、実際の引数、戻り値を記述します。戻り値がない場合は「なし」と明記します。複数の処理をコードと一対一で逐語的に写すのではなく、読み手が全体の流れを把握できる粒度にします。

### 標準キー

日本語のキーは次を標準とします。

- クラス: `責務`、`フィールド`、必要に応じて`処理`
- 関数・メソッド: `責務`、`処理`、`引数`、`戻り値`
- 必要な場合のみ: `副作用`、`エラー`、`補足`

同じ意味のキーを一つのコメント内で重複させません。任意項目を空欄で機械的に埋めません。宣言名と責務の対応、フィールド名・引数名と実装の対応を明確にします。

### 説明の合格基準

JSON-likeの項目が揃っているだけでは合格にしません。コメントだけを先に読んだ人が、宣言の使いどころと利用契約をつかめることを必須にします。

- **責務**には「何を対象に、何のために、何をするか」を書きます。「管理する」「処理する」「確認する」だけで対象を省きません。
- **処理**には重要なデータの流れ、判断条件、結果を意味のある単位で書きます。「関数Aを呼び、結果を返す」というコードの読み上げだけにしません。
- **引数**には呼び出し元が渡す値の意味を書きます。名前や型の繰り返しで終えず、単位・許容範囲・未設定値の意味が重要なら明記します。
- **戻り値**には呼び出し側が使う意味を書きます。`bool`、`None`、状態名など複数の結果がある場合は、どの条件で何を返し、呼び出し側がどう解釈するか示します。
- **フィールド**には保持する状態の意味と、いつ・誰が使う値かを書きます。フィールド名を日本語へ置き換えただけにしません。
- 略語・専門語・プロジェクト独自の用語は、読者が知らない可能性がある場合、初出で意味を説明します。説明文は自然な日本語を基本にし、識別子やAPI名だけ英語で残します。
- 読者がコードを見なければ分からない前提・制約・重要な理由は、宣言コメントか通常コメントに明記します。自明な構文はコメントしません。

コメントを読んでも「対象は何か」「いつ成立するか」「結果は何を意味するか」のいずれかが分からない場合は、説明不足として差し戻します。

### 不合格例

```text
責務: [_is_allowed_action: アクションを確認する]
処理: [1: IDを確認する 2: true/falseを返す]
引数: [action_id: ID]
戻り値: [bool: 結果]
```

どの操作IDを何と照合するか、真偽値が何を許可するかが書かれていません。記法は揃っていますが、説明としては不合格です。

### 合格例

```text
責務: [
  _is_allowed_action: 選択された操作IDが、現在の画面で実行を許可された候補に含まれるか判定する
]
処理: [
  1: 選択された操作IDを許可候補一覧と照合し、一覧外の操作を実行経路へ進ませない
]
引数: [
  action_id: 判断を返したモデルが今回の実行対象として指定した操作ID
  allowed_action_ids: 現在の画面で実行候補として許可された操作IDの一覧
]
戻り値: [
  bool: 操作IDが一覧に含まれる場合True、含まれない場合False
]
```

### Pythonの例

```python
# {
#   責務: [
#     FrameAnalyzer: 画面フレームから文字や操作部品を検出し、判断側が使う候補へまとめる
#   ]
#   フィールド: [
#     recognizer: 画面内の文字列と位置を読み取り、候補のラベル作成に使う認識器
#   ]
# }
class FrameAnalyzer:
    # {
    #   責務: [
    #     AnalyzeFrame: 有効な画面フレームから候補を作り、候補がない場合も空の一覧で返す
    #   ]
    #   処理: [
    #     1: 幅・高さ・画素形式を検証し、後続処理で読み取れないフレームを除外する
    #     2: 文字列と画面部品を検出し、それぞれの位置と認識確信度を得る
    #     3: 検出結果を操作候補へまとめ、ラベル・種類・領域を候補選択側へ渡す
    #   ]
    #   引数: [
    #     frame: 幅・高さ・画素形式と画素データを持つ解析対象の画面
    #   ]
    #   戻り値: [
    #     candidates: 候補のラベル・種類・画面内領域・認識確信度を持つ一覧。未検出時は空の一覧
    #   ]
    #   エラー: [
    #     ValueError: 幅または高さが正でない、あるいは画素形式を解析器が扱えない
    #   ]
    # }
    def analyze_frame(self, frame: Frame) -> list[Candidate]:
        ...
```

    //   処理: [
    //     1: 幅・高さ・画素形式を検証し、後続処理で読み取れないフレームを除外する
    //     2: 文字列と画面部品を検出し、それぞれの位置と認識確信度を得る
    //     3: 検出結果を操作候補へまとめ、ラベル・種類・領域を候補選択側へ渡す
    //   ]

## 通常コメント

- 意味のある処理単位ごとに、処理の目的・理由・前提・安全上の境界を通常コメントで説明します。
- 宣言コメントの`処理`は全体の流れ、通常コメントは実装内部の処理単位や理由を説明します。両者を1対1で一致させません。
- コメントをコードの逐語的な言い換えにしません。コードから分からない理由、制約、意図を優先します。
- 自明な代入や単純なreturnまで一行ずつコメントしません。意味のある処理単位に説明が付いているかをレビューします。
- コメントを変更した場合は、実装との一致を必ず確認します。

## エラーと失敗処理

- 失敗を握りつぶさず、呼び出し元が判断できるエラー、結果型、ログなどで伝えます。
- 捕捉する例外やエラーの種類を必要な範囲に限定し、原因と対象が分かる情報を残します。
- リソース確保後に失敗する経路では、確保済みリソースを解放します。
- 入力・対象・状態を検証し、実入力や破壊的操作など安全上重要な失敗では、危険側へ継続せず明示的に停止します。
- エラー時に部分更新が起こり得る場合は、原子性、復旧、再試行の可否を設計してテストします。

## アルゴリズムと実行性能

- 対象データ量、呼び出し頻度、時間制約を考慮し、処理量とメモリ使用量が妥当なアルゴリズムを選びます。
- 画面フレーム処理、判断ループ、UI応答など頻度の高い経路では、不要な全件走査、重複計算、ブロッキングI/O、コピーを避けます。
- 新しい計算・キャッシュ・並行処理は、正しさと失敗時の挙動をテストし、性能効果や複雑さを根拠とともに説明します。
- 実測が必要な性能主張は、代表的な入力と再現可能な測定方法を示します。根拠のない「高速化」や、測定なしの性能回帰容認をしません。

## 拡張性と既存契約

- 既存の公開API、ファイル形式、schema、C ABI、Provider契約をIssueの要求なしに破壊しません。
- 複数の実装を差し替える必要がある境界は、安定したインターフェースで分離します。
- 新しい依存関係や抽象化を追加する場合は、必要性、保守コスト、既存の拡張点で代用できない理由を説明します。
- 一つの将来案のためだけに過剰設計せず、要求された拡張経路は具体的に確保します。

## テスト、CI、E2E

- バグ修正には、可能な限り修正前に失敗する再現テストを追加します。再現できない場合は理由と代替検証を記録します。
- 新しい振る舞いには正常系、境界値、失敗系、安全上必要な状態遷移をテストします。
- 影響範囲に応じた単体・統合・E2Eテストを選び、ユーザーの実操作に関わる経路はE2E結果を確認します。
- 必須CIを通過させます。チェックを無効化、削除、緩和する変更は、同等以上の検査を導入し、その理由をIssueとPRに記録しない限り行いません。
- 実行できなかったテストは未確認とし、実行済み・成功と報告しません。
- テストが不安定、順序依存、外部環境依存の場合は、原因を記録し再現性を改善します。

## 仕様書、設計書、利用者向け説明

人が使う説明資料は、原則として以下を読者が把握できる順に書きます。

1. 背景: なぜこの説明・機能が必要か
2. 目的: 何を実現するか
3. 手段: どう実現するか、どの制約があるか
4. 利用者の操作: どこで何を入力・選択・実行するか、何が表示されれば成功か

操作がない項目は、その旨を明記します。仕様書・設計書には前提、対象範囲、失敗時の挙動、未決事項も必要に応じて記載します。

- 利用者に操作を求める場合は「選択してください」「実行してください」のように書きます。
- アプリの動作は「アプリは候補を表示します」「失敗時は停止状態になります」のように書きます。
- 一文に複数の条件や操作を詰めず、短い自然な日本語と一貫した用語を使います。
- コードやIssueを開かなくても説明資料単独で目的と基本操作を理解できるようにします。
- コード、仕様、画面表示、実際の動作を一致させます。

## 変更の完了

新しい機能はIssueの範囲で実装・検証し、必要なドキュメントを更新してGit管理します。レビュー時は[レビュー基準](./レビュー基準.md)を適用し、プロジェクトの[開発ワークフロー](./ワークフロー/ワークフロー.md)に従います。
