# 判断パイプライン

`DecisionPipeline` は観測Sourceから読み込んだ画面とAutomation候補へOCR候補を加え、`CandidateMerger`、`GamePlayerEngine` の順に接続する。呼び出し側は `run()` だけで判断と履歴保存まで実行できる。各段階は個別に差し替え可能で、現段階では実際のOS入力は行わない。

## Decision Reliability検証

### 背景

小型LLMは候補外Action、別snapshotへの参照、現在画面と矛盾したstate参照を返すことがあります。Decision Providerの自己申告だけでは、判断を現在の観測へ結び付けられません。

### 目的

`DecisionVerifier` はProviderの出力を実行前に検査します。候補選択の信頼性とAction Safetyを分離し、判定根拠を後から追跡できるようにします。

### 手段

検証器は出力のschema/type、Action EvaluatorとDecision Context双方の許可候補ID、Decision Contextと現在画面の一致、snapshot・screen・state参照、選択理由とActionの明示的な矛盾を決定論的に検査します。検査結果は `TRUST` / `CAUTION` / `VERIFY` / `REJECT` とEvidence・provenanceを持ちます。`REJECT` はDecision traceへ記録して処理を停止します。Action Safety監査記録にも独立した `decision_reliability` fieldとして引き渡し、Safety判定へ混ぜません。意味理解を行う追加Verifierは対象外です。

### 利用者の実行方法

利用者は既存のPlay画面から判断実行を開始してください。追加設定は不要です。アプリはdry-runでは非REJECTの判断を記録できます。実入力では `TRUST` 以外の判断や追加確認が必要な操作を実行しません。実行前に止めた判断は監査traceに理由を残しますが、実行済み操作の履歴や次画面のOutcome評価には加えません。利用者はゲーム固有データdirectoryの `decision_trace.json` と `action_safety.json` で判定・Evidenceを確認してください。
