# 判断パイプライン

`DecisionPipeline` は観測Sourceから読み込んだ画面とAutomation候補へOCR候補を加え、`CandidateMerger`、`GamePlayerEngine` の順に接続する。`run()` は判断と履歴保存までを行う。`run_and_execute()` は既定のdry-runまたは明示許可した実入力を行い、対象・安全・停止条件を検査する。各段階は個別に差し替え可能である。

判断traceは最初に `planned` として保存する。実行後の `ExecutionReceipt` を同じsnapshot・action・世代へ関連付け、正常送信を確認したものだけを実操作履歴へ投影する。dry-run・入力前失敗・旧形式の送信不明な判断は実行済み扱いにしない。実操作後は `complete_execution_observation()` を明示呼出しし、最後の操作も終端終了前に記録する。送信開始後の例外は `dispatch_unknown` として監査し、成功や未送信を推測しない。APIと検証範囲は [実行受領記録](architecture/execution_receipts.md) を参照する。

## Decision Reliability検証

### 背景

小型LLMは候補外Action、別snapshotへの参照、現在画面と矛盾したstate参照を返すことがあります。Decision Providerの自己申告だけでは、判断を現在の観測へ結び付けられません。

### 目的

`DecisionVerifier` はProviderの出力を実行前に検査します。候補選択の信頼性とAction Safetyを分離し、判定根拠を後から追跡できるようにします。

### 手段

検証器は出力形式と型、Action EvaluatorとDecision Context双方の許可候補ID、判断時の画面・状態と現在画面の一致、選択理由とActionの明示的な矛盾を決定論的に検査します。結果には `TRUST` / `CAUTION` / `VERIFY` / `REJECT` の状態と、確認した根拠・出所を記録します。

理由が `Do not click on Start under any circumstances`、`Do not press the Start button yet`、`Start should not be clicked` のように、候補のクリック・押下を明示的に拒否している場合も矛盾として検出します。否定表現の後ろに続く説明語の種類で検出を制限せず、候補一覧にある `Start Over` のような長い別候補名は、選択された `Start` と区別します。

- `TRUST`: 実施した検査を通過しました。判断が絶対に正しいことを保証する状態ではありません。
- `CAUTION`: 判断理由などの情報が不足しているため、慎重な扱いが必要です。
- `VERIFY`: 画面や状態の参照情報が不足しているため、追加確認が必要です。
- `REJECT`: 出力形式、許可候補、画面状態などの検査に失敗したため、判断を拒否します。

`REJECT` はDecision traceへ記録して処理を停止します。Action Safety監査記録にも選択判断の検査結果を `decision_reliability` として引き渡します。これは操作自体の危険度とは別の記録です。意味理解を行う追加Verifierは対象外です。

### 利用者の実行方法

利用者は既存のPlay画面から判断実行を開始してください。追加設定は不要です。アプリはdry-runでは非REJECTの判断を記録できます。実入力では `TRUST` 以外の判断や追加確認が必要な操作を実行しません。実行前に止めた判断は監査traceに理由を残し、行動履歴から除外します。直前に実行した操作のOutcome結果は、その操作のtraceへ記録して次の判断にも引き継ぎます。Outcomeの `state_changed` は、終端結果とは分け、状態変化と安定のEvidenceを重み付けして判定します。競合が強く判定を保留した場合は状態変化として扱いません。利用者はゲーム固有データdirectoryの `decision_trace.json` と `action_safety.json` で判定・Evidenceを確認してください。
