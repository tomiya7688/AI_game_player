# 日本語の設計図と説明書を更新するとき

[リポジトリのREADMEへ戻る](../../README.md) ｜ [既存のRuntime境界の説明](../architecture/runtime_layers.md)

この手順は、ゲームの実装が変わったときに「分かりやすい図は古い実装を説明している」という問題を防ぐためのものです。図の色や見た目だけでなく、**何が実装されているか、通常の処理からつながるか、実機で確認したか**を区別して直します。

## 正本を増やさない

- 人が理解するための全体図・局所図は `doc/guide/`、`doc/models/`、`doc/architecture/*_for_readers.md` に、現行と予定を区別して記述する。
- 細かな各機能の仕様は、既存の`doc/*機能説明書.md`などの説明書を参照し、同じ仕様の正本を複製しない。
- クラス図・呼出し図・Repository Mapの**コードから生成する資料**は既存の`tools/generate_docs.py`と、その設定・テストを使う。新しい生成器を並行して作らない。
- Model Manifest、学習能力、来歴などの機械向け台帳は、それぞれの既存契約や[#277](https://github.com/tomiya7688/AI_game_player/issues/277)を正本候補とし、読み物の表と二重登録しない。

## 何が変わったら、どこを見直す？

| 実装で変更したこと | 見直す説明 |
|---|---|
| 画面取得方法・OCR・候補の統合 | 画面認識の局所図と手法カード、モデル配置図、失敗経路 |
| 判断先・評価器・結果評価 | 判断の流れ、結果評価の優先順位、モデル配置と根拠 |
| モデルや外部Providerの追加 | 実行基盤・入力形式・モデル識別子、対応可能／選択済み／実呼出しの区別 |
| 操作実行・緊急停止・安全確認 | 安全の境界図、拒否・停止後の古い結果、実機テスト根拠 |
| 記録・学習用データ・モデル更新 | 保存から学習までの図、採用と元に戻す条件、プライバシー |
| クラス名・呼出し関係 | 既存の生成コード図と対応するテスト |

図の矢印には、渡す情報（画面、候補、許可、結果など）と、制御かデータの意味を言葉で示します。凡例では実線・点線を使い分け、色だけでは区別しません。通常の経路を見直すときは、実装・テストの場所と基準コミットを更新してください。

## 改修の確認手順

リポジトリ直下で、次のコマンドを実行します。Python標準ライブラリだけでできる範囲の確認なので、重いモデルやWindowsゲームの起動は必要ありません。

```powershell
python -m unittest discover -s tests -p "test_source_navigation.py" -v
python -m unittest discover -s tests -p "test_generate_docs.py" -v
python tools/generate_docs.py --check
```

最初のテストはルートREADME・ソース索引・既存の`doc/architecture/runtime_layers.md`を必須として調べます。存在する`doc/guide/`・`doc/models/`、人向けのRuntime図、この更新手順も検査対象へ加えます。ローカルMarkdownリンクの参照先とリポジトリ外へのリンクを検査し、インラインリンクの任意タイトル、山括弧や括弧を含む参照先、参照形式のリンク定義を扱います。コードスパン・コードフェンス・HTMLコメント内の例は実際のリンクとして検査しません。

コードフェンスはバッククォートとチルダに対応し、開始と同じ文字で開始時以上の長さの閉じフェンスを要求します。Mermaidでは既知の図形式（フロー、シーケンス、クラス、状態図など）とフローノードの重複定義を調べます。図のコメントや引用ラベルをノード定義に数えません。欠けた参照先、閉じ忘れ、実際の重複定義の失敗テストと、正常なタイトル・コード例・図コメントの回帰テストがあります。**外部URLの到達性、見出しアンカーの存在、Markdown全仕様、文章の意味、Mermaid描画エンジンによる厳密な構文までは検査しません。**

`generate_docs.py --check` は既存のコード由来の生成物が変更元と一致するかを確認します。古い場合は `python tools/generate_docs.py` で更新し、生成差分をレビューしてください。人が書く図まで機械生成の正しさに任せないでください。

上のうち、リンクとMermaidの軽量検査は`bug-ci`の通常のPR検査へ接続します。CIが通ったことはWindows実機や図の読みやすさを保証しません。

## 人が必ず確認すること

- 図をGitHub上で開き、文字が小さすぎないか、切れていないか、線が交差して意味を誤認しないかを目視確認する。通常幅と狭い画面幅を見る。
- 日本語を読んだ人が「誰が、何を受け取り、いつ何を選び、失敗時にどうするか」を説明できるか確認する。英語の名前だけを並べていないか見る。
- モデル名が設定にあるだけなのに、今回の推論で使ったモデルとして書いていないか確認する。
- 部品の存在、通常経路への接続、実機での動作試験を別々の状態として記録する。機材・日時・設定・基準コミットを残す。
- 実装が元Issueで指定された手法を省いていないか確認する。省いた場合は理由と残作業のOpen Issueを残す。
- 画面・操作・モデル・保存・ネットワークへの接続に関係する変更では、個人情報の扱いと安全の境界を省略しない。

## この検査の限界

リンクが正しいことと、参照されたソースが図の意味どおりに動くことは別です。Mermaidのノード名が揃っていても、図の制御順が正しいとは限りません。根拠に挙げたテストファイルが存在するだけで、今回そのテストが成功したとも限りません。実行しなかった試験・確認しなかった実機条件は「未確認」と書いてください。

例えば「これを実行すれば安全になる」は、対象、条件、確認範囲が分からないため不合格です。「このコマンドは相対リンク先ファイルの存在を確認します。ゲームへの入力や実機での停止動作は確認しません」と書けば、読者は検査の操作と限界を区別できます。

図で赤と緑の色だけに「未実装／実装済み」を対応させる例も不合格です。各ノードへ状態の文字を付け、凡例に実線・点線の意味と確認コミットを示してください。狭い表示で文字が切れる場合は、図を局所図へ分けて再確認してください。表示物の生成・レンダリング確認は静的検査の成功と分けて記録します。

PRでは既存テンプレートの資料確認欄を使ってください。「対応可能／選択済み／実行済み」や「部品／実行接続／実機確認」の記載、図と実装の意味の一致、根拠の有効性は人が確認します。これらを自動判定したという扱いにはしません。人向け資料全体の未達条件は#606、指定手法と完了条件の自動強制は#508へ追跡し、別の承認基盤やモデル台帳を作りません。

文書全体の完了条件は[#606](https://github.com/tomiya7688/AI_game_player/issues/606)、整合性確認の継続作業は[#614](https://github.com/tomiya7688/AI_game_player/issues/614)で追います。
