# 開発者と評価者が使うGitHub Issue・Pull Request手順

この文書は、AI Game Playerの開発者がGitHub Issueから変更を作り、Pull Request（PR）で確認を受ける手順を説明します。GitHub Issueが要求・優先度・設計上の決定を管理し、`doc/versions.md`が実装済み変更を記録します。開発予定ファイルはIssueの代わりに使いません。

## 複数AI・人が共同で作業するときの共通ルール

このリポジトリは、人、Claude Code、Codex、ChatGPT、GitHub Copilotが同じ`main`へ変更を入れます。どの作業者も、次のルールを例外なく守ります。コーディング規約は[共通コーディングルール](../コーディングルール.md)に従います。

### 作業者ごとの入口

| 作業者 | 最初に読まれる指示ファイル | 補足 |
|---|---|---|
| Codex | `AGENTS.md` | 自動で読み込まれます。 |
| Claude Code | `CLAUDE.md` | `AGENTS.md`への案内を含みます。 |
| GitHub Copilot | `.github/copilot-instructions.md` | `AGENTS.md`への案内を含みます。 |
| ChatGPT（チャット） | なし | リポジトリを直接変更できません。人が`AGENTS.md`とこの文書を会話に貼って作業を依頼します。ChatGPTが出した変更は、リポジトリを操作できる作業者がこの手順でPRにします。 |

### 必ず守る順序

1. **毎回、作業開始時にpullする。** セッションを始めるたびに、`git fetch origin main`を実行します。`main`をcheckoutしている場合は`git pull --ff-only origin main`も実行します。fetchやpullに失敗した場合は、最新状態を確認できていない事実を報告し、古い状態へ変更を重ねません。
2. **Issueを占有する。** 着手前に、Issueに他の作業者のオープンなPRまたはブランチがないことを`gh pr list --search "ISSUE番号"`と`git branch -r`で確認します。なければ、Issueへ「着手: 作業者名、ブランチ名」とコメントします。他の作業者が着手済みのIssueは変更しません。
3. **1 Issue = 1 worktree = 1 branch = 1 PR。** 最新`origin/main`から専用worktreeを作ります。ブランチ名は`作業者名/issue-番号-要約`（例: `claude/issue-418-baseline`）にします。他の作業者のworktreeや未コミット変更を編集・削除しません。
4. **実装とテスト。** コーディングルールに従い、関連テストと`doc/versions.md`を更新します。
5. **PR作成の直前にもう一度pullする。** `git fetch origin main`の後、`origin/main`が進んでいれば`git merge origin/main`で取り込み、競合を解消して関連テストを再実行します。
6. **自己レビューする。** 後述の「自己レビュー」を、コミット前に`git diff origin/main...HEAD`に対して実施します。
7. **PRを作る。** `finish_task.bat`が成功してから、PR本文に自己レビュー結果を記載して作成します。
8. **CIを確認する。** push・pull_request両eventの必須workflowがすべて成功し、未解決のreview threadがないことを確認します。失敗や未完了があればマージせず、原因を直して再確認します。
9. **問題がなければマージする。** CIが全て成功し、自己レビューに未解決の指摘がない場合だけ、マージします。マージ後、`main`をfast-forwardします。
10. **終了を記録する。** 完了したIssueはPRに`Closes #番号`を付けるか、完了条件が残る場合はIssueへ残作業をコメントします。途中で止める場合も、到達点・残作業・未確認事項をIssueへコメントします。

### マージしてはいけない場合

- 必須CIに失敗、未完了、skipped、欠落がある。
- 未解決のreview threadがある。
- 自己レビューで指摘を残している、またはコーディングルールに違反している。
- 他の作業者が同じIssueまたは同じファイルを変更中で、競合を解消していない。
- 変更の安全性（実入力の既定有効化、Safety / Verifierの迂回）を確認できていない。

マージできない場合は、PRをDraftにして理由をPRとIssueへ記録し、作業者または人に引き継ぎます。`--no-verify`、`--admin`、`main`へのforce pushでCIやレビューを回避しません。

### 自己レビュー

PR作成前に、`git diff origin/main...HEAD`の全体を読み、[自己レビューの観点](../コーディングルール.md#自己レビューの観点)の7項目を順に確認します。確認結果はPR本文の「Self-review」欄に、観点ごとに「問題なし」または「指摘と対応」として記録します。自分が書いたコードの確認結果を、テストやCIが成功しているという理由だけで省略しません。確認できなかった項目は「未確認」と書きます。

### 他の作業者のPRをレビューする場合

別の作業者のPRを確認するときは、同じ7観点で差分を読み、問題をPRのコメントで具体的な行と修正案つきで伝えます。他の作業者のブランチへ直接pushしません。

### コミットの帰属表示

コミットメッセージとPR本文には、変更した作業者を識別できる`Co-Authored-By`または生成元の表示を付けます。付け方は各作業者の既定に従います。

## 開発者がIssueからPRを作る手順

1. `git fetch origin main`を実行し、作業開始時点の`main`を確認します。`main`をcheckoutしている場合は`git pull --ff-only origin main`も実行します。リモート取得に失敗した場合は、最新状態を確認できていないことを記録し、古いworktreeへ変更を重ねません。
2. 対象Issueの優先度、完了条件、関連コメントを読みます。Issue本文が不足する場合は、実装に関係するコメントと対象コード・テストだけを追加で確認します。
3. `start_task.bat --issue 番号`を実行し、Issueに対応する短い作業コンテキストを生成します。Issue番号は実際のGitHub Issue番号に置き換えます。
4. 最新`main`から隔離worktreeと作業ブランチを作り、Issueの完了条件を満たす最小の変更を実装します。既存checkoutの未コミット変更を上書きしません。
5. 変更に対応するテストと文書を更新します。利用者・実装者向け説明では、対象、前提、操作、結果、確認方法を具体的に書きます。リリースノートには`doc/versions.md`の`Unreleased`へIssue番号と実装済みの振る舞いを追加します。
6. 対象を絞ったテストを実行し、コミット前に`finish_task.bat`を実行します。生成文書、lint、型検査、unit test、compile、静的checker、性能checker、workflow security checker、`git diff --check`がすべて成功した場合にだけコミットします。
7. `finish_pr.bat "commit message" next-branch`を実行します。`finish_pr.bat`は`finish_task.bat`、commit、push、PR作成、CI・review確認、merge、`main`のfast-forward、次のbranch作成をこの順で実行します。専用worktreeでIssue一件だけを変更し、実行前に`git status`で他の変更が混ざっていないことを確認します。CIやreview threadの確認で停止した場合は問題を解消し、同じコマンドを再実行します。staged変更がなければ`finish_pr.bat`は現在branchの既存PRを再利用して確認をやり直します。
8. `finish_pr.bat`はPR作成後にGitHub CLIの`gh pr checks --watch --fail-fast`でCIの完了を待ちます。status checkはGitHubがPRのhead commitに対して報告するCI結果です。続けて全status checkの状態をJSONで取り直し、少なくとも一件のcheckがあり、すべてが`pass`の場合だけ次へ進みます。pending、failed、cancelled、skipped、未対応状態、checkなし、CLI/APIエラーはmergeを停止します。
9. `finish_pr.bat`はGitHub GraphQL APIからPRのinline review threadを全ページ取得します。inline review threadは差分のファイル行に付いたreview commentと返信のまとまりです。未解決threadがある場合、ファイル位置、投稿者、本文を表示してmergeを停止します。Kadoka reviewのinline commentがない場合は、追加reviewの投稿を待ちません。
10. CIとreview threadの条件を満たした後、merge gateは固定headのpush・pull_request Workflow RunをREST APIで個別取得します。必須workflowの各eventについて最新runの現在attemptがcompleted/successの場合だけ、確認済みhead commit SHAを`gh pr merge --match-head-commit`へ渡します。待機中のhead更新、run欠落・未成功、API取得や解析の失敗もmergeを停止します。
11. `finish_pr.bat`はmerge成功後だけ`main`へ戻り、`git pull --ff-only origin main`でfast-forwardし、指定された次branchを作ります。merge状態が確認できない場合は後続のbranch切替を行いません。

`finish_pr_merge.py`はCIと未解決inline review threadを検査してmergeを実行する補助ツールです。単体テストは成功・非成功check・checkなし・review commentなし・未解決comment・認証失敗・head更新を確認します。GitHub接続、認証情報、外部APIが停止した場合の実動作は、GitHub Actionsと手元のGitHub CLI認証で確認してください。

`language-ci`のLua・.NET・JavaScript / TypeScript jobは、先行するソース検出jobの結果を検証します。対象ソースがない場合は、検査対象がない理由をログに記録してjobを成功終了します。対象ソースがある場合だけ、その言語の環境構築と検査を実行します。検出結果が空または`true` / `false`以外の場合は失敗します。この区別により、対象ソースがない正常なPRでも全check成功を要求でき、実際に`skipped`となったjobはmerge gateで拒否できます。check一覧だけをpush・PR両eventの独立した証拠とは扱いません。

event別の検証対象は`tests.yml`、`language-ci.yml`、`safety-ci.yml`、`fail-safe-ci.yml`、`bug-ci.yml`、`performance-ci.yml`、`upd-architecture-ci.yml`の7 pathです。`tools/pr_workflow_evidence.py`は同じheadのpush・pull_requestを100件ずつ取得し、作成時刻（同時刻はrun ID）でpath/event別に最新runを選びます。古い成功で新しい失敗やpendingを隠さず、現在のrun_attemptを検査します。件数変動・不完全page・重複ID・別head/event/repo/PR・1000件上限到達を検出した場合は停止するため、証拠を取得できないforkやPR associationが欠落した応答も成功扱いにしません。未完了なら完了後にコマンドを再実行してください。

必須workflowを追加・削除・改名した開発者は、`REQUIRED_WORKFLOW_PATHS`とこの一覧を更新してください。テストは実際のworkflowファイルとの一致を検査します。event別検証はworkflow単位の読み取りであり、全jobの独立取得やGitHub側の原子的なmerge保護ではありません。check・inline review・最後のhead照合も合わせて検査します。

## 評価者がIssueへフィードバックを記録する手順

1. 評価者は対象の機能、再現条件、期待する結果、実際の結果を確認します。
2. 既存Issueに該当する問題があれば、そのIssueへ具体的な根拠と再現条件を追記します。該当するIssueがない場合は、一つの修正単位ごとにIssueを作ります。
3. 評価者は確認していない挙動を実装済みと断定せず、GUI・実入力・CIなど未実施の検証を明記します。

## GitHub Actions workflow security checker

`tools/workflow_security_check.py`は`.github/workflows/`のYAML workflowを走査します。`finish_task.bat`と`.github/workflows/tests.yml`のPython quality jobがcheckerを実行するため、開発者は同じ規則をローカルとCIで確認できます。checkerは通常のゲーム実行経路からimportされません。

checkerはトップレベルの`permissions`欠落、`write`または全scope権限、`pull_request_target`・`workflow_run`、`run`内のevent/input/step-output/secret直接展開、`actions/checkout`のcredential永続化、`workflow_run`からのartifact download、Reusable workflowへの`secrets: inherit`を検出します。Reusable workflowは、別workflowをjobの`uses`から呼び出して処理を共有する機能です。workflowのtoken権限は必要なread scopeだけにし、読み取りだけを行うcheckoutには`persist-credentials: false`を設定します。[`actions/checkout@v4`の説明](https://github.com/actions/checkout/blob/v4/README.md)では、既定でGit認証情報をローカルGit設定へ保存し、この入力を`false`にすると保存を無効化します。

検出した例外を一時的に許可する場合は、例外となるYAML行に規則ID、有効期限、理由を記載します。トップレベル`permissions`欠落の例外は、workflowの1行目に理由コメントを書きます。有効期限はUTCの日付で、期限当日までは有効です。理由は10文字以上で書きます。期限切れ、理由不足、別規則IDの例外コメントは検出結果を抑止しません。

```yaml
permissions:
  contents: write # workflow-security: waive WFS002 until=2026-12-31 reason="release workflow publishes signed artifacts"
```

このcheckerはYAML構造を行とインデントから検査し、GitHub Actions expressionが`run` script本文へ直接入る形を検出します。環境変数へ渡された値の後続処理やthird-party Action内部の実装までは追跡しません。shellで外部入力を使う場合は、environment経由で受け取り、コマンドの引数として安全に扱えるよう検証・引用します。Actionのcommit SHA固定は別Issue #268の対象です。

## 回帰テストとcoverage

`language-ci`のLua・.NET・JavaScript/TypeScript jobは、先行jobが返した対象ソースの有無を検証します。検出値が`false`なら、そのjobは対象なしをログへ記録して成功します。検出値が`true`なら、従来のsetup・構文検査またはbuild・testを実行します。検出値が空または`true`/`false`以外なら失敗します。対象なしによる成功は、その言語の実ソースを検査したことを意味しません。レビューではjobの結論だけでなく、対象あり・なしのログも区別してください。

- バグ修正では可能な限り修正前に失敗する再現テストを追加し、PRに元Issueとテスト名を記載する。再現できない場合は理由と代替検証を記載する。
- Python coverageはbranch modeで計測し、初回実測約71%に対してCI最低70%をbaseline floorとする。floorを下げる場合は理由をPRで説明し、通常は維持または引き上げる。
- Native coverageは現時点でC ABI contract testが少数のため未導入。対象コードとテスト群が広がった段階でgcov/llvm-covを再評価する。
