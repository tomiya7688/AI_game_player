# 開発者と評価者が使うGitHub Issue・Pull Request手順

この文書は、AI Game Playerの開発者がGitHub Issueから変更を作り、Pull Request（PR）で確認を受ける手順を説明します。GitHub Issueが要求・優先度・設計上の決定を管理し、`doc/versions.md`が実装済み変更を記録します。開発予定ファイルはIssueの代わりに使いません。

## 開発者がIssueからPRを作る手順

1. `git fetch origin main`を実行し、作業開始時点の`main`を確認します。リモート取得に失敗した場合は、最新状態を確認できていないことを記録し、古いworktreeへ変更を重ねません。
2. 対象Issueの優先度、完了条件、関連コメントを読みます。Issue本文が不足する場合は、実装に関係するコメントと対象コード・テストだけを追加で確認します。
3. `start_task.bat --issue 番号`を実行し、Issueに対応する短い作業コンテキストを生成します。Issue番号は実際のGitHub Issue番号に置き換えます。
4. 最新`main`から隔離worktreeと作業ブランチを作り、Issueの完了条件を満たす最小の変更を実装します。既存checkoutの未コミット変更を上書きしません。
5. 変更に対応するテストと文書を更新します。利用者・実装者向け説明では、対象、前提、操作、結果、確認方法を具体的に書きます。リリースノートには`doc/versions.md`の`Unreleased`へIssue番号と実装済みの振る舞いを追加します。
6. 対象を絞ったテストを実行し、コミット前に`finish_task.bat`を実行します。生成文書、lint、型検査、unit test、compile、静的checker、性能checker、workflow security checker、`git diff --check`がすべて成功した場合にだけコミットします。
7. `finish_pr.bat "commit message" next-branch`を実行します。`finish_pr.bat`は`finish_task.bat`、commit、push、PR作成、CI・review確認、merge、`main`のfast-forward、次のbranch作成をこの順で実行します。専用worktreeでIssue一件だけを変更し、実行前に`git status`で他の変更が混ざっていないことを確認します。CIやreview threadの確認で停止した場合は問題を解消し、同じコマンドを再実行します。staged変更がなければ`finish_pr.bat`は現在branchの既存PRを再利用して確認をやり直します。
8. `finish_pr.bat`はPR作成後にGitHub CLIの`gh pr checks --watch --fail-fast`でCIの完了を待ちます。status checkはGitHubがPRのhead commitに対して報告するCI結果です。続けて全status checkの状態をJSONで取り直し、少なくとも一件のcheckがあり、すべてが`pass`の場合だけ次へ進みます。pending、failed、cancelled、skipped、未対応状態、checkなし、CLI/APIエラーはmergeを停止します。
9. `finish_pr.bat`はGitHub GraphQL APIからPRのinline review threadを全ページ取得します。inline review threadは差分のファイル行に付いたreview commentと返信のまとまりです。未解決threadがある場合、ファイル位置、投稿者、本文を表示してmergeを停止します。Kadoka reviewのinline commentがない場合は、追加reviewの投稿を待ちません。
10. CIとreview threadの条件を満たした後、`finish_pr.bat`は確認済みhead commit SHAを`gh pr merge --match-head-commit`へ渡します。待機中にPRのheadが更新された場合はmergeを停止し、checkを再確認します。CI・PR状態・review情報の取得や解析に失敗した場合もmergeしません。
11. `finish_pr.bat`はmerge成功後だけ`main`へ戻り、`git pull --ff-only origin main`でfast-forwardし、指定された次branchを作ります。merge状態が確認できない場合は後続のbranch切替を行いません。

`finish_pr_merge.py`はCIと未解決inline review threadを検査してmergeを実行する補助ツールです。単体テストは成功・非成功check・checkなし・review commentなし・未解決comment・認証失敗・head更新を確認します。GitHub接続、認証情報、外部APIが停止した場合の実動作は、GitHub Actionsと手元のGitHub CLI認証で確認してください。

## 評価者がIssueへフィードバックを記録する手順

1. 評価者は対象の機能、再現条件、期待する結果、実際の結果を確認します。
2. 既存Issueに該当する問題があれば、そのIssueへ具体的な根拠と再現条件を追記します。該当するIssueがない場合は、一つの修正単位ごとにIssueを作ります。
3. 評価者は確認していない挙動を実装済みと断定せず、GUI・実入力・CIなど未実施の検証を明記します。

## GitHub Actions workflow security checker

`tools/workflow_security_check.py`は`.github/workflows/`のYAML workflowを走査します。`finish_task.bat`と`.github/workflows/tests.yml`のPython quality jobがcheckerを実行するため、開発者は同じ規則をローカルとCIで確認できます。checkerは通常のゲーム実行経路からimportされません。

checkerはトップレベルの`permissions`欠落、`write`または全scope権限、`pull_request_target`・`workflow_run`、`run`内のevent/input/step-output/secret直接展開、`actions/checkout`のcredential永続化、`workflow_run`からのartifact download、Reusable workflowへの`secrets: inherit`を検出します。Reusable workflowは、別workflowをjobの`uses`から呼び出して処理を共有する機能です。workflowのtoken権限は必要なread scopeだけにし、読み取りだけを行うcheckoutには`persist-credentials: false`を設定します。[`actions/checkout@v4`の説明](https://github.com/actions/checkout/blob/v4/README.md)では、既定でGit認証情報をローカルGit設定へ保存し、この入力を`false`にすると保存を無効化します。

検出した例外を一時的に許可する場合は、例外となるYAML行に規則ID、有効期限、理由を記載します。トップレベル`permissions`欠落の例外は、workflowの1行目に理由コメントを書きます。有効期限はUTCの日付で、期限当日までは有効です。理由は10文字以上で書きます。期限切れ、理由不足、別規則IDの例外コメントは検出結果を抑止しません。

```yaml
permissions:
  contents: write # workflow-security: waive WFS002 until=2026-12-31 reason="release workflow publishes signed artifacts"
```

このcheckerはYAML構造を行とインデントから検査し、GitHub Actions expressionが`run` script本文へ直接入る形を検出します。環境変数へ渡された値の後続処理やthird-party Action内部の実装までは追跡しません。shellで外部入力を使う場合は、environment経由で受け取り、コマンドの引数として安全に扱えるよう検証・引用します。Actionのcommit SHA固定は別Issue #268の対象です。

## 回帰テストとcoverage
- バグ修正では可能な限り修正前に失敗する再現テストを追加し、PRに元Issueとテスト名を記載する。再現できない場合は理由と代替検証を記載する。
- Python coverageはbranch modeで計測し、初回実測約71%に対してCI最低70%をbaseline floorとする。floorを下げる場合は理由をPRで説明し、通常は維持または引き上げる。
- Native coverageは現時点でC ABI contract testが少数のため未導入。対象コードとテスト群が広がった段階でgcov/llvm-covを再評価する。
