## このアプリは何をするもの？

ゲームの画面を見て、次にできそうな操作を探し、どれを選ぶか決め、その操作の後で画面がどう変わったかを確かめるためのアプリです。人がゲームをするときの「見る→考える→操作する→結果を見る」を、役割の異なる部品で繰り返します。

**最初からゲームを勝手に操作するわけではありません。** 初期状態の実入力は無効です。確認運転（dry-run）では操作を選んでも実際のキーやマウス入力を送らず、どう判断したかを記録します。実入力には別の許可が必要です。

> **このページの範囲：** 2026-10-31のmainコミット \`4d8ae6f\` で標準構成を読み取った説明です。すべての拡張機能やモデルを網羅した図ではありません。Windows実機、モデル読み込み、実ゲームでの再現試験をこの資料のために実行したものではありません。

## 図1：一回の操作は、どの順番で進む？

\`\`\`mermaid
flowchart TD
    A["新しい画面を見る"] -->|画像と画面の情報| B["文字や画像から操作候補を探す"]
    B -->|候補| C["候補を評価し、使ってよい候補を絞る"]
    C -->|新しい画面と前回の記録| D["前回の操作がどうなったかを確かめる"]
    D -->|結果も含む判断材料| E["今回の操作候補を選ぶ"]
    E -->|回答| F["回答が許可候補と一致するか検査する"]
    F -->|検査を通った候補| G["危険な操作や停止状態でないか確かめる"]
    G --> H{"実入力の許可がある？"}
    H -->|いいえ| I["確認運転：入力せず記録"]
    H -->|はい| J["実際の入力を送り、結果を記録"]
    I --> K["次の画面を観測する"]
    J --> K
    K --> A
\`\`\`

*青い箱や矢印などの色は意味の条件ではありません。矢印の言葉が「何を渡すか」、ひし形が「ここで分かれる条件」です。実行拒否・停止・候補なし・取得失敗では、図の通常経路を続行しません。*

ここで大事なのは、**前回の操作が成功したかどうかを、新しい画面から確かめる**ことです。キー入力を送れたことと、ゲームの目標を達成できたことは別です。候補の評価、AIによる判断、実行の許可も別です。

## 図2：部品はどこにある？

\`\`\`mermaid
flowchart LR
    P["利用者"] -->|目的と設定| U["画面と操作ボタン"]
    subgraph APP["アプリ内：主にPython"]
      U -->|開始・停止| S["一回の処理を組み立てる部分"]
      S -->|観測の依頼| O["画面取得と認識"]
      O -->|画面・候補| S
      S -->|候補・前回の結果| D["判断と結果評価"]
      D -->|選んだ候補| S
      S -->|検査済みの候補| X["安全確認と入力"]
      X -->|入力・拒否の記録| R["履歴と保存"]
    end
    O -->|画面を取得| W["対象のゲーム画面"]
    X -->|許可時だけ入力| W
    D -.->|利用者が選択した場合だけ| L["Ollama：アプリとは別のサービス"]
\`\`\`

**実線：** 現行の基本経路を説明する線。**点線：** 指定した場合に限る任意の接続。実行するPCが同じか別かは設定と実環境によるため、外部PCへの接続を自動で動くものとして描いていません。C++による前処理も、部品の存在と標準の自動接続を分けて調べる必要があります。

## 図3：どこで学習済みモデルを使う？

\`\`\`mermaid
flowchart TD
    A["画像の明るさ・特徴を調べる"] --> B["規則で計算：モデルなし"]
    C["画像から文字を読む"] --> D["Tesseract：任意の認識器・言語データ"]
    E["次の操作を選ぶ"] --> F{"設定で判断先を選ぶ"}
    F -->|初期設定| G["ローカル規則：モデルなし"]
    F -->|Ollamaを選択| H["Ollama：モデルを動かすサービス"]
    H -->|モデル名を指定| I["例：gemma3:4b"]
\`\`\`

\`gemma3:4b\` は**設定欄の初期値**であり、常に読み込まれ、実行されているモデルという意味ではありません。画像認識に対応するモデルであっても、現在の判断依頼が画像そのものを送る仕組みとは限りません。どのモデルを実際に動かしたかは、起動時の設定や実行記録で別に確認します。

さらに詳しい役割図・モデル台帳は [#608](https://github.com/tomiya7688/AI_game_player/issues/608) と [#609](https://github.com/tomiya7688/AI_game_player/issues/609) で整備します。ここにある三つの図は、初めて読む人向けの**簡略図**です。

## 具体例：「開始」という文字を見つけたとき

1. 新しい画面に「開始」という文字があり、文字を読む処理が位置の候補を返したとします。
2. アプリは位置や候補の情報を調べます。「文字がある」だけで、安全に押せるボタンと断定しません。
3. 前回の操作があれば、今回の新しい画面を見て、その操作の結果も判断材料に含めます。
4. 規則または選択されたモデルが候補を一つ提案しても、候補の照合と安全確認を飛ばしません。
5. 確認運転なら入力は送りません。実入力を許可した場合も、操作後に次の画面を改めて観測します。

これは**説明用の例**であり、実ゲームで「開始」を検出・クリックできたという試験結果ではありません。

## 資料を読むときの三つの見分け方

- **部品が存在する**：コードがある状態です。利用者の通常の操作から必ず呼ばれるとは限りません。
- **通常の流れからつながっている**：起動して、その部品へ進む経路をコードで確認した状態です。実機での成功保証ではありません。
- **実際の環境で確認した**：機材、日時、設定、入力、記録がそろった試験結果です。上の二つだけでは証明できません。
